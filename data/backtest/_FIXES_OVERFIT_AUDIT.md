# 본 컨텍스트 수정의 케이스피팅/과적합 감사

> 2026-06-17. 사용자 질문: "케이스바이케이스로 하나씩 고치는 거냐? 피팅한 위험 없나?" 70~78차
> 수정 9건을 범용(근본)인지 케이스(6사 땜질)인지 정직 분류 + 매직넘버 튜닝 여부 + cross 커버리지 갭.

## 결론 (먼저)

- **8/9는 범용 근본수정** — 값을 데이터·DART스키마·playbook에서 받아 전 회사 적용. 표본 밖 회사로 확인.
- **1/9 (cross_statement)는 케이스 불완전** — 메커니즘은 범용이나 **데이터가 KB에 나온 4개만**. 같은
  근본원인 OCI id가 **54개인데 4개만 등록**(50개 미수정). 땜질 위험 실재.
- **매직넘버는 과적합 아님** — 전부 출력 크기 바운드(토큰·표시), 6사 통과용 정답 임계 없음.

## ★ cross_statement 커버리지 갭 (케이스피팅 실증)

```
OtherComprehensiveIncome id 중 SCE 단독등록(=CIS서 강등 위험): 54
  내가 cross 등록(고침):                                          4
  미등록(같은 근본원인, 안 고침):                                50
```

- **4/54 = KB에 나온 것만 고쳤다.** 종속·관계기업 OCI지분(Share…OtherComprehensive)·재평가
  (Revaluation)·지분상품 공정가치변동(ChangeInFairValue) 등 **50개가 같은 결함**으로 CIS서 강등 잔존.
- 즉 cross 데이터는 **6사 표본이 표면화한 증상만** 메운 케이스바이케이스. 클래스 전수 아님.

### 범용 대안 (제안 — 54개 수기 대신 명명규칙)

OCI 표시 id `…OtherComprehensiveIncomeNetOfTax<X>`와 CIS canonical이 쓰는
`GainsLossesOn<X>NetOfTax`는 **같은 개념의 표시형/손익형 쌍**이다. id 명명규칙으로 자동 페어링하면
54개를 수기 등록 없이 일괄 구제 가능(§3, 진짜 근본). 현 4개 수기 등록은 그 전 단계 땜질.

## 매직넘버 스캔 (튜닝 여부)

| 값 | 위치 | 성격 | 튜닝? |
|----|------|------|-------|
| confidence 0.7 | to_alias_additions | 사람확인 필터 기본값 | 아님(사람이 최종) |
| limit 12 / 30 / 350 / 20 / 10 | 후보·발췌·timeline 캡 | 토큰/표시 바운드 | 아님(크기 제한) |
| 금액패턴 `\d{1,3}(,\d{3}){2,}` | G6 | 천단위 2그룹=금액 식별 | 아님(일반 휴리스틱) |

- 정답을 가르는 임계(6사 PASS용)는 **없음**. 전부 출력 크기·표시 바운드 → 과적합 아님.

## 회귀가드 (케이스수정 누적에도 유지)

- 백테스트 발굴 recall **5/6** 불변(70~78차 전 구간). 정상 거짓양성 거동 불변(삼성 cross=0).
- pytest **262 passed·1 xfailed**(누적). 각 수정 RED→GREEN + 무회귀.

## 종합 판정

- 대부분(8/9) 근본수정이라 케이스피팅 아님. 매직넘버 튜닝 없음. 회귀가드 유지.
- **단 cross_statement 데이터는 케이스 불완전(4/54)** — 다음 단계로 **명명규칙 기반 일괄 구제**(또는
  54 전수 등록)로 클래스 전체를 덮어야 진짜 근본. 현 상태는 KB 증상만 메운 땜질로 명시.
