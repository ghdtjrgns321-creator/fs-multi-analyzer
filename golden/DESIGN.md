# 골든테스트 설계 — PHASE2 파이프라인 외부정답 검증

> 설계 단일출처. 이 폴더(`golden/`)는 PHASE2(멀티에이전트 교차검증) 파이프라인이
> "실제로 잘 도는가"를 **외부 정답**에 대조하는 골든테스트를 담는다.
> 관련 메모리: `golden-test-strategy`. 상위 설계: [docs/agent/PHASE2_DESIGN.md](../docs/agent/PHASE2_DESIGN.md).

## 1. 문제 — 왜 골든테스트인가

PHASE2를 "숫자 맞고 LLM 결과도 그럴듯함"으로 검증했다고 할 수 없다. 재현·반증이 안 되기 때문이다.
그렇다고 두 가지 손쉬운 대안은 각각 함정이 있다.

- **내 이전 실행을 정답으로 봉인** → 순환. 버그까지 정답으로 잠근다. (회귀 감지에는 유효하나
  "옳은가"는 답하지 못한다.)
- **사람이 filing마다 정답지 작성** → 불가능. 1,659사 규모에서 지속 불가.

해법은 정답을 **DART와 현실**에서 가져오는 것이다. 검증 질문을 둘로 쪼갠다.

| 검사                     | 질문                                     | 정답 출처         | 자동화             |
| ------------------------ | ---------------------------------------- | ----------------- | ------------------ |
| **검사1 수치 골든**      | 카드에 찍힌 수치가 실제 DART 값과 같은가 | DART 그 자체      | 전자동, 전 회사    |
| **검사2 의심 적중 골든** | 실제로 의심스러운 걸 의심스럽다고 했는가 | 재작성·제재(현실) | 고정 벤치마크 세트 |

두 검사는 독립이며 구축 순서도 검사1이 먼저다(정답지 조달 비용 0, LLM 비용 0).

### 1.1 전후관계 꼬임과 그 해소 (검사2 전제)

사용자 지적: "DART 공시자료는 다 지적·수정을 거친 정정본인데, 그걸 정답으로 매기면 전후관계가
꼬인다." 정정 반영된 데이터를 도구에 주고 "왜 못 잡았냐"고 채점하면 이상이 이미 지워진 뒤라
부당하다.

**실측으로 해소됨.** DART는 정정 후에도 원본 접수분을 지우지 않는다. `list(final=False)`로 정정
이력을 포함한 전체 목록을 받으면 최초 접수번호가 남아 있고, 그 번호로 본문·XBRL 둘 다 서빙된다.

- 실측(2026-07-12): 00117212 2020 사업보고서, 원본 rcept=`20210322001065`.
  `document()` 본문 4,372,004 bytes(재무제표·주석 포함), `finstate_xml()` XBRL zip 251,858 bytes
  다운로드 성공, 2024-04-18 재작성 정정본(`20240418000399`)과 본문 해시 상이.
- 재현 스크립트: `golden/probes/probe_asfiled.py`(오늘 실측분 이관 예정).

따라서 **입력 = 원본 접수분(as-filed) 고정, 정답 = 그 뒤에 온 정정·제재.** 미래 정보가 입력으로
새지 않는 point-in-time 구조. 인과가 깨끗하다.

## 2. 검사1 — 수치 골든 (전자동, 정답지 = DART)

LG생건 27장 전수 감사(메모리 `lghh-e2e-card-audit-defects`)에서 사람이 눈으로 한 "카드 수치 ↔
DART 원값" 대조를 코드로 만든다. 한 번 만들면 아무 회사에나 공짜로 붙는다.

### 2.1 대상 — 카드에 찍히는 모든 수치

최종 카드(`AccountFinding`)와 그 표시 데이터(`dashboard/card_data.py`)에서 수치가 나오는 지점:

| 지점             | 코드 경로                                                   | 성격         |
| ---------------- | ----------------------------------------------------------- | ------------ |
| 근거 표 금액     | `card_data.evidence_rows` → `numeric_evidence[].value`      | 원값         |
| 주장 인용값      | `card_data.claim_lines` → `claims[].cited_value`            | 원값(문자열) |
| 분해표 leaf/소계 | `decomposition.rows[].delta`, `child_residual`, `residual`  | 계산값       |
| 시계열 추이      | `card_data.series_points` → `account_level_series[].amount` | 원값         |
| 서술 속 축약금액 | `card_data.humanize_amounts` 출력                           | 환산 표시    |

### 2.2 역추적 — 이미 있는 인프라 재사용

`src/report/grounding.py`가 핵심을 이미 만들어 뒀다.

- `build_account_index(account_series, unmapped, note_facts, sce_cells, note_disclosures)` →
  `{계정 식별자: {원 단위 절대값 집합}}`. 원천은 `load_normalized_financials`(DuckDB
  `normalized_financials`, 회사/연도 격리) + 주석 fact + SCE 셀 + 서술형 공시.
- `_sig_amount` / `_matches_scaled` → 인용 단위(조·억·백만·천원·원)를 해석해 **원 단위로 복원**한 뒤
  자릿수까지 대조(허용오차: 상대 1% 또는 절대 100만원). 예전의 유효숫자(trailing-zero 제거)
  대조는 1,961억과 1,961백만을 같은 값으로 봐서 스케일 오류를 통과시켰다.

기존 grounding은 **LLM 출력(의심건)** 을 카드 조립 *전* 에 검증한다. 검사1은 같은 인덱스를
**최종 카드**(모든 변환 이후: `amounts.format_krw` 환산, `series_normalize` 표기정규화, 분해
산술)에 적용한다. 그래서 grounding이 못 보는 변환 버그를 잡는다.

### 2.3 두 하위검사

**1a. 원값 실재.** 카드의 모든 수치(2.1 전부)가 그 계정의 인덱스 풀에 자릿수까지 맞게 있는가.
LG생건 감사에서 원값 100% 일치를 확인한 그 검사의 코드판.

**1b. 환산 무결.** 화면에 찍힌 사람용 표기(`fmt_krw`/`format_krw`/`humanize_amounts` 출력)를
다시 파싱한 값이 그 원값과 같은가. LG생건 **결함②**(1조 2,534.7억을 1,253.47억으로
÷10 축소)를 정확히 겨냥한다. 원값과 표시가 어긋나면 FAIL.

분해표는 추가로 산술 항등도 본다: `Σleaves == 부모 delta`(부동소수 오차 내), 각 leaf 값은 1a로
원천 대조. `card_data.waterfall_leaves`가 이미 이 항등을 유지하도록 설계돼 있어 재사용한다.

### 2.4 PASS/FAIL 임계 (측정 가능)

| 항목         | PASS 조건                                 | FAIL                      |
| ------------ | ----------------------------------------- | ------------------------- |
| 1a 원값 실재 | 대조 대상 수치 전수 불일치 = 0            | 1건이라도 값 불일치       |
| 1b 환산 무결 | 표시↔원값 불일치 = 0                      | 1건이라도 어긋남          |
| 분해 산술    | 카드별 \|Σleaves − 부모 delta\| ≤ 1원     | 초과                      |
| 대사 불능    | 역추적 불가 수치를 **목록으로 명시 출력** | silent 통과(§9 위반)      |

"대사 불능"(인덱스에 계정 자체가 없어 대조 불가)은 통과도 실패도 아닌 **제3 버킷**으로, 반드시
산출물에 목록화한다. 조용히 통과시키면 hollow-PASS다. 대사 불능 건수가 임계(예: 카드당 0건)
초과면 인덱스 커버리지 갭으로 별도 조사.

### 2.5 산출물

- 하니스: `golden/numeric/check_numeric.py` — 저장된 카드(`suspicion_cards.json`) + 정규화 DB를
  입력받아 수치별 대조표를 생성.
- 대조표: `golden/numeric/_report_{corp}_{year}.md` — N행(수치 하나=1행), 열=[카드, 계정, 표시값,
  원값, 원단위 절대값, 판정(match/convert_fail/unreconcilable)]. 분모 N과 불일치 M을 헤더에 박는다.
- pytest 래퍼: `golden/numeric/test_numeric_golden.py` — 벤치마크 회사에 대해 M=0, 대사불능=0 단언.

## 3. 검사2 — 의심 적중 골든 (as-filed 벤치마크)

"실제로 의심스러운 것"의 정답지는 현실이 이미 만들어 뒀다. **입력은 원본 접수분(§1.1)으로 고정**한다.

### 3.1 정답지 출처

| 출처             | 정답 신호                                       | 전후꼬임              | 비중       |
| ---------------- | ----------------------------------------------- | --------------------- | ---------- |
| ① 제재·감리 확정 | 금감원이 분식 확정한 회사·연도의 지적 계정/영역 | 원본 수집 시 없음     | 주력       |
| ② 재작성 정정    | t년 값이 t+1·t+2에서 실제로 바뀐 계정           | as-filed 입력 시 없음 | 주력(자동) |
| ③ 주입(합성)     | 우리가 심은 이상(원천적으로 정답 확정)          | 없음                  | 보조       |

②는 사람 라벨링 0으로 자동 생성된다. 프로젝트는 이미 `src/collect/correction.py`(정정 이력·재작성
연도)와 `src/report/series_normalize.py`(t년 당기값 vs t+1 보고서 전기값 대조 → `restated_later`)를
갖고 있어, 보유 corpus에서 "값이 실제로 바뀐 계정"을 코드로 뽑을 수 있다.

**등록 조건 (전후꼬임 방지 게이트).** 벤치마크 사례로 올리기 전 반드시:
`우리 DB의 t년 값 == 최초 접수분(as-filed)의 t년 값`이 대조로 확인돼야 한다. 확인 안 되면
그 사례는 버린다(우리 데이터가 이미 정정본일 수 있으므로). 조건은 코드로 검사 가능하다.

③ 주입은 전후꼬임에서 완전히 자유로운 유일한 출처다. 단, 현실 분식의 교묘함보다 단순할 수 있어
보조로 둔다(주력은 ①②).

### 3.2 채점 — 텍스트 비교 금지, 존재+순위

LLM 문구는 매 실행 달라진다. 그래서 문구를 비교하지 않고, **정답 계정/영역이 카드 큐에 있는가와
그 순위**만 본다. 비결정론이어도 점수가 안정적이다.

- **적중 판정**: 정답 계정의 `series_key`(또는 canonical)가 어떤 카드의 `numeric_evidence`/`claims`
  앵커로 상위 K 카드 안에 등장 → 적중.
- **순위**: `card_data.sort_cards`/`group_cards`가 정하는 카드 순서상 위치.
- **지표**: recall@K = 정답 계정 중 상위 K 큐에 든 비율(M/N, 분모=정답 계정 수).

### 3.3 대조군 (거짓양성 억제)

아무 일 없던 정상 회사에서 상위 카드가 과도하게 뜨지 않는지 본다. FP 정의는 자동화가 어려우므로
프록시를 쓴다: **정상 대조군의 상위 K 카드 수 ≤ 임계**(회사당 절대치, 예: 상위 위험 카드 ≤ 기준선).
기준선은 백테스트 정상군 분포에서 고정한다.

### 3.4 PASS/FAIL 임계 (측정 가능)

| 항목        | PASS 조건                                                 | FAIL          |
| ----------- | --------------------------------------------------------- | ------------- |
| 재작성 적중 | recall@K ≥ 목표치(초기 세트로 baseline 고정 후 회귀 금지) | baseline 미만 |
| 제재 적중   | 지적 영역이 상위 K에 존재 (M/N, 분모=벤치마크 회사 수)    | 목표 미만     |
| 대조군 FP   | 정상군 상위 카드 수 ≤ 기준선                              | 초과          |

K와 목표 recall은 **초기 벤치마크 세트 실측으로 baseline을 고정**하고(첫 측정 = 기준선 선언),
이후 그 baseline 대비 회귀를 FAIL로 삼는다. 절대 목표치를 미리 리터럴로 박지 않는다(§3 범용 원칙).

### 3.5 벤치마크 세트 (초기 후보)

보유 corpus 스캔으로 확보된 재작성 정정 후보:

- **00117212** — 2017~2020 연결재무제표 재작성(rcept `202404180003xx` 계열).
- **00258801** — 2020~2022 재무제표 재작성(rcept `202403200003xx` 계열).
- 백테스트 기존 분식 6사 → Phase2 카드 단위로 확장(as-filed 여부 재확인 필요).
- 정상 대조군 ~5사(재작성·제재 이력 없음).

각 사례는 `golden/hit/benchmarks.yaml`에 [corp, year, 원본 rcept, 정답 계정/영역, 등록조건 통과여부]로
등록한다. 정답 계정은 정정 헤더/재표시 대조에서 자동 추출하되, 최종 등록은 사람이 승인(§9).

### 3.6 산출물

- 정답지 빌더: `golden/hit/build_labels.py` — corrections + series_normalize 재표시에서 정답 계정
  자동 추출 + 등록조건 게이트.
- 하니스: `golden/hit/check_hit.py` — as-filed 입력으로 `build_suspicion_cards(report, run_llm=True)`
  실행 → 카드 큐 ↔ 정답 대조 → recall@K·FP 산출.
- 채점표: `golden/hit/_score_{corp}_{year}.md` — 정답 계정별 [계정, 적중여부, 순위], 헤더에 recall@K.
- 실LLM 배치: 릴리스 전 1회. 비용은 벤치마크 세트 크기에 비례(회사당 대략 ₩1~2천, PHASE2 실측 기준).

## 4. 전제 인프라 — as-filed 원본 수집

검사2가 서려면 원본 접수분을 재무·주석 모두 원본으로 가져와야 한다. §1.1에서 서빙 가능성은
실측했다. 남은 구현 격차는 하나다.

- **본문·주석 XBRL**: `opendart.document(rcept)` / `finstate_xml(rcept)`가 원본 rcept로 동작 확인됨.
  기존 수집 경로 재사용 가능.
- **재무제표 본표(격차)**: `opendart.finstate_all`(JSON API)은 버전 선택 불가 — 항상 최신본을
  준다. 정정된 벤치마크 회사는 **원본 XBRL zip에서 본표를 추출**하는 경로가 필요하다. 프로젝트가
  이미 Arelle로 주석 XBRL을 파싱하므로(`src/collect/notes_xbrl.py`) 본표 추출 확장은 현실적이다.
- **원본 rcept 식별**: `opendart.filings(corp, start, end)`(`final=False`)에서 "정정" 미포함 최초
  사업보고서 행 = 원본. 오늘 실측 로직을 `golden/asfiled/resolve_original.py`로 정착.

이 인프라는 검사2 벤치마크 회사에만 쓰므로(전 corpus 아님) 비용이 제한적이다.

```
golden/
  DESIGN.md              # 이 문서(설계 단일출처)
  asfiled/               # 원본 접수분 수집 인프라(검사2 전제)
    resolve_original.py  #   원본 rcept 식별
    fetch_original.py    #   원본 본문·XBRL 수집 + 본표 추출
  numeric/               # 검사1 — 수치 골든
    check_numeric.py     #   카드 수치 ↔ DART 원천 대조
    test_numeric_golden.py
  hit/                   # 검사2 — 의심 적중 골든
    build_labels.py      #   정답지 자동 생성 + 등록조건 게이트

    check_hit.py         #   as-filed 입력 채점
  probes/                # 실측 스크립트(재현용)
    probe_asfiled.py
```

## 6. 구현 순서

1. **검사1 먼저**(정답지·LLM 비용 0). 2.2 인덱스 재사용 → 저장된 카드에 1a/1b 적용 →
   대조표 산출 → 벤치마크 회사 M=0 단언. 아무 회사에나 즉시 적용되는 자동 감사가 붙는다.
2. **as-filed 인프라**(§4). 원본 rcept 식별 + 원본 XBRL 본표 추출.
3. **검사2**. 정답지 빌더(등록조건 게이트) → 채점 하니스 → 초기 세트로 baseline 고정 → 릴리스 전
   실LLM 배치.

## 7. 비범위 (YAGNI)

- **LLM 자체 품질 회귀**(프롬프트 변경으로 관점이 헛소리 시작)는 검사1·2가 못 잡는다. 검사2가
  적중률로 부분적으로만 방어한다. 별도 관점 품질 테스트는 이번 범위 밖.
- **전 corpus 검사2 채점**: 비용상 금지. 고정 벤치마크 세트만.
- **환율·통화 정규화 정답**: 이미 게이트가 비KRW를 차단(별개 이슈).
- **분기·세그먼트 데이터**: DB 미수집(DATA_SCOPE 한계) — 정답지에서 제외.
