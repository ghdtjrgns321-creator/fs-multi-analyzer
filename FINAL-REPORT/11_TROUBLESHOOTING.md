## 11.2 대표 사고 흐름 — id_label_conflict (원인→확산→피해→복구)

```
[원인] 회사가 XBRL account_id 슬롯에 라벨과 다른 실질 신고
       예: dart_BondsIssued(발행사채) 슬롯에 "주식발행초과금" 라벨
                    │
[매퍼 판정] id-first 원칙 → account_id를 신뢰(가짜 exact_taxonomy_match)
                    │
[확산] 부호·BS 항등식은 통과 (금액은 맞으니까)
       → 기계검산이 구조적으로 못 봄 (검산의 사각)
                    │
[피해] 1.4조가 발행사채→자본으로 둔갑 (00148504)
       9개 청크에서 독립 출현 = systematic
                    │
[발견] 홀리스틱 전수통독 101사/383 회사연도 (raw 원본 LLM 직접 통독 = 도구 밖 검증)
                    │
[복구] label_priority 데이터에 충돌 계정 등록 (자본금·주식발행·만기보유·투자부동산)
       → map_row가 label 우선 → 110+ 회사연도 자동 교정
       → 회귀 pytest·recall 5/6 무악화 확인
```

## 11.3 교훈 (재발 방지 원칙)

- **검산이 통과해도 안심하지 않는다** — 금액이 맞아도 계정 정체성이 뒤집힐 수 있다. 부호·항등식 통과는 "구조가 옳다"의 증명이 아니다.
- **검사 범위 ≠ 데이터 범위** — grand 축만 고치고 member 셀을 방치하면 334건이 남는다. 수정의 범위를 데이터의 범위에 맞춘다.
- **도구 경계 ≠ 감사 경계** — 추적표(도구)가 SCE 2D·CIS→IS를 안 보면 정상이 거짓양성으로 뜬다. 도구의 사각을 감사의 사각으로 착각하지 않는다.
- **자기참조 검증은 사각을 못 본다** — "도구 안에서 도구 검증"은 도구가 못 보는 것을 영원히 못 본다. raw 원본을 LLM이 직접 통독하는 것이 도구 밖 검증이다.
- **대량 신호는 로직 전에 전처리를 의심한다** — 정상 노이즈 309개는 로직이 아니라 floor 계산 시점(소계 제외 후)의 문제였다.
- **변환 오류는 "어떤 진실을 무시하나"를 먼저 묻는다** — 사후 정규식 스크러빙이 아니라, 각 변환 경계가 이미 보유한 더 권위있는 데이터(재표시 전기값·원단위 원값·공시 원문 라벨)를 권위로 승격한다.
- **실패를 성공으로 둔갑시키지 않는다** — quota로 관점이 전멸하면 "0건 위험없음"이 아니라 failed로 표면화한다. 작은 표본의 "수렴"도 착시일 수 있다(16번째 후 105사 더 봐야 진짜 수렴).
- **한글 파일은 최소 패치 + diff로 mojibake 확인** — 서브에이전트가 U+FFFD를 옮겨 훅에 걸린 사례에서, 라운드트립·bulk 치환을 금하고 최소 패치로 처리한다.
- **식별자 칸에 표시문구를 넣지 않는다** — 상태는 상태 컬럼으로, 이름은 이름대로. 식별자가 표시문구로 오염되면 하류의 모든 `없으면 라벨` 폴백이 조용히 죽는다(자본거래 병합의 뿌리).
- **실패 실행은 결과를 남기지 않는다** — 실패의 빈 결과가 이전 정상 산출물을 덮으면 다음 세션엔 재조사할 증거가 없다. 저장·완료 마커는 완주에만.

## 11.4 "해당 사고 기록 없음"

성능·비용 폭증으로 인한 운영 중단, 데이터 유실로 인한 롤백, 레이트리밋 초과로 인한 서비스 장애는 이 프로젝트 문서에 기록이 없다 — 아직 단일 회사 단위의 개발·검증 단계이고 운영 전수 실행을 하지 않았기 때문이다(Phase2 실호출은 표본 측정만). 비용은 회사당 ₩300~2,000 수준으로 관리되며, DART 무료 API·회사/연도 격리 DuckDB 구조가 대규모 장애 표면을 애초에 줄인다. 없는 사고를 지어내지 않는다.
