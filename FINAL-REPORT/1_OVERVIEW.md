# 1. 개요 — 무엇을, 왜, 어떻게

## 1.1 문제 정의 — 어떤 실패를 막나

상장사가 공시한 재무제표(재무상태표 BS 중심 + 손익 IS·현금흐름 CF·주석)에는 감사인이 검토해야 할 리스크 신호가 숨어 있다. 그러나 두 가지 실패가 그 신호를 놓치게 만든다.

- **숫자만 보는 도구의 한계** — 계정 하나의 이상치만 보면, 재무제표 *간*의 모순(매출은 늘었는데 영업현금흐름은 줄었다)이나 전기 대비 *변화*(주석 문구가 커졌다)를 놓친다.
- **LLM에 통째로 넣는 접근의 한계** — 재현성(매번 다른 답·숫자 환각), 전수성(토큰 한계로 일부만), 앵커링(학습 선입견), 일관성(회사마다 흔들림)이 무너진다. (근거: 자매 프로젝트 #1에서 LLM 산술 정확도가 Gemini 20~40% vs gpt-4.1-mini 100%로 양립 불가 확인, PLAN §3.1)

이 도구는 두 실패를 동시에 막는다. **재무제표 간 흐름(BS-IS-CF 사슬)** 과 **전기 대비 변화**를 결정론 코드로 전수 계산하고, "무엇이 의심스러운가"의 발견만 여러 관점의 LLM에 맡겨 교차검증한 뒤, 감사인이 검토할 **리스크 후보 카드**를 근거와 함께 제시한다.

> **부정을 확정하지 않는다.** "이 회사는 분식이다"가 아니라 "감사인이 봐야 할 재무제표 리스크 신호"를 제시하는 review 도구다. 목적은 분식 탐지가 아니라 **이상 변화·감사인 검토 큐**의 생성이다(HANDOFF_NOW, PHASE1_EXIT_GATE). 백테스트 분식 recall은 목적 잣대가 아니라 회귀 가드일 뿐이다.

## 1.2 왜 이 접근인가 — 대안 대비

| 관점      | 통상적 접근                   | 본 프로젝트                                      |
| --------- | ----------------------------- | ------------------------------------------------ |
| 계산      | LLM이 증감률·비율을 직접 계산 | **결정론 코드/SQL이 계산**, LLM은 해석만         |
| 발견      | 규칙으로 이상 유형 전수 열거  | 열린 도메인이라 **LLM이 발견**, 코드는 앵커      |
| 관점      | 한 AI가 전부 판단             | **6개 독립 관점** 교차검증(충돌이 신호)          |
| 근거      | LLM 서술을 신뢰               | 모든 주장에 **EvidenceRef 코드 검증**(환각 탈락) |
| 계정 지식 | 코드에 하드코딩               | **config YAML 외부화**(계정은 데이터로 흐름)     |

핵심 통찰: 계정은 산업마다 무한 증식하지만(건설사 미청구공사, 금융사 대출채권), **검증 관점은 닫힌 집합**이다. 그래서 에이전트 축은 관점(역할)에만 대응시키고, "이번 회사에서 어떤 계정을 볼지"는 신호엔진이 데이터로 동적 선정한다(PLAN §3 원칙2).

## 1.3 5원칙 — 설계 헌법

이후 모든 설계가 종속되는 5개 원칙(PLAN §3).

| #   | 원칙                                  | 무엇을 강제하나                            | 코드 증거                                                |
| --- | ------------------------------------- | ------------------------------------------ | -------------------------------------------------------- |
| 1   | **계산은 코드, 발견은 LLM**           | 숫자 계산을 LLM에 안 맡김                  | `src/signals`·`analysis_tools` 결정론, 수집·정규화 LLM 0 |
| 2   | **에이전트는 역할, 계정은 데이터**    | 데이터 차원을 에이전트화 금지(추가 게이트) | `PerspectiveName` 6개 닫힌 집합, 계정은 series로 흐름    |
| 3   | **계정 지식은 플레이북(데이터)**      | 항등식·관계사슬·프롬프트를 YAML로          | `config/` YAML 15개(playbooks 9 + 루트 6)                |
| 4   | **LLM은 풀되 사실에 앵커링**          | tool DSL + grounding + 반박                | `grounding.py`·`vocab_guard.py`·`rebuttal.py`            |
| 5   | **수준(level)과 변화(change)를 함께** | 전기 대비 변화를 1급 축으로                | `series_normalize`·`metrics_panel` occurrence_state      |

## 1.4 아키텍처 레이어 (L0~L6)

```
L0   수집        OpenDART: 재무제표 JSON + 주석 XBRL(TSV) + 사업보고서 원문 XML
L1   정규화      XBRL 계정 → canonical account tree (약 2,015종) + mapping confidence
L1.5 주석 인덱서  주석 → 섹션 분류 + 전기/당기 정렬 + note diff + 계정↔섹션 매핑
     [온보딩 게이트]  G1~G8·통화 결정론 검문(+G6 dump) — L1→L2 관문, UI "분석 준비"가 자동 실행
     [LLM 전처리]  별칭 자동 보정(코드 후보→LLM 선택→신뢰도≥0.7만 자동 등록) + 본문 통독 서술추출 — 카드 단계 진입 조건
L2   신호엔진    결정론: materiality + 관계사슬 + QoE + 변화 + 변동분해 + 커버리지 원장
L3   역할에이전트 LLM 5관점(발견) — 수치·주석·흐름·추세·동종. tool DSL·EvidenceRef
L4   리포트      의심건 카드(근거·반박·조사·외부검증·다음절차) 종합
L5   Human       검토 큐로 카드 게시 — 감사인이 검토 (review queue 철학)
```

L1.5와 L2가 토대다. 나머지 레이어는 모두 이 출력에 얹힌다. 이후 이 도구는 **전처리 엔진**(LLM 전처리+Phase1)을 2-Layer(리더=읽기 / 분석가=판단)로 재정의했다(DISCLOSURE_DECOMPOSITION_DESIGN, 10장 참조).

## 1.6 포트폴리오 3부작 포지셔닝

이 프로젝트(#3)는 감사의 3개 층위를 나눠 갖는 3부작의 마지막이다(PLAN §2).

|             | #1 k-ifrs-1115    | #2 local-ai-assist | #3 multi-BS (본 프로젝트) |
| ----------- | ----------------- | ------------------ | ------------------------- |
| 분석 대상   | 기준서·사례(지식) | 전표 모집단(미시)  | **공시 재무제표(거시)**   |
| 데이터      | 텍스트(RAG)       | 합성 전표          | **실제 공시(DART)**       |
| AI 패러다임 | 가둔다(환각방지)  | 룰 기반 스크리닝   | **멀티에이전트 교차검증** |
| 도메인 성격 | 닫힘(정답지 있음) | 반열림(룰 기반)    | **열림(정답지 없음)**     |

#3은 #2의 최대 약점(실데이터·label 부재)을 실제 DART 공시로 보완하고, #1의 자산(PydanticAI 구조화 출력)·#2의 자산(DuckDB·config-driven 룰·검토후보 포지셔닝)을 재활용한다.
