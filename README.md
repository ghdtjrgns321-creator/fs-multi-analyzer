#### 분석 대상 및 포지셔닝

- 분석 대상 데이터 : 최근 5개년 연결 및 별도 재무제표, 주석(XBRL), 사업보고서 원문
- 포지셔닝 : 감사인의 전문가적 판단을 돕는 공시 데이터 분석 도구

### 2. 문제 인식

#### 재무제표 전수 검토의 한계

- 방대한 검토 데이터 : 단일 기업 1개년(연결/별도, 주석, 사업보고서 등) 기준에 매년 시계열까지 더해져 검토량 증가
- 공시 정보 구조의 이질성 : 재무제표, 주석, 서술형 문서의 형식이 달라 수동 대조 시 정보 누락 위험
- 비표준화된 검토 방식 : 검토자의 역량, 경험에 따라 분석 결과 편차 발생

#### 범용 LLM 분석의 한계

- 재현성 : LLM 직접 연산 → 수치 환각 발생 위험
- 일관성 : 응답 생성 시마다 분석 논리와 방향 변동
- 정보 누락 : 원문 직접 투입 → 임의적 데이터 누락 발생 위험
- 비교 가능성 : 회사별, 연도별 비교 어려움

### 3. 프로젝트 기능 및 기대 효과

| 데이터 전수 스캔           | 5개년 전체 계정 전수 분석 → 유의미한 항목만 검토단계로 승격                    |

#### 핵심 설계 원칙

- **연산/분석 역할 분리**
  - 코드 연산 : 증감률, 비율, 기여도 등 수치 연산은 알고리즘으로 처리 → 수치 환각 가능성 원천 차단
  - LLM 분석 : 코드로 산출된 결과값을 받아 의미 해석 및 주요 쟁점 식별
- **관점은 5개로 고정, 계정은 데이터로 흐른다**
  - 발견 관점 5개 : 재무 수치 · 주석 · 계정 간 관계 · 시계열 추세 · 업종 비교
  - 어떤 계정을 볼지는 계산 결과가 정하고, 관점을 계정별로 늘리지 않음
  - 외부검증은 발견자가 아니라 카드 확정 후의 검증자 — 화면 라벨 6개 중 1개
- **사실 대조로 환각 차단**
  - 관점이 인용한 금액을 원 단위로 복원해 실제 장부값과 자릿수까지 대조
  - 장부에 없는 계정·금액을 든 지적은 사유를 남기고 탈락

## 1. 문제 인식

### 읽을 대상을 어떻게 줄이나

| 단계       | 남는 대상                             | 줄이는 방법                    |
| ---------- | ------------------------------------- | ------------------------------ |
| 원본       | 5개년 × 본표 5종 × 전 계정 + 주석     | —                              |
| 계산(코드) | 계정별 지표 · 관계 신호 · 비율 시계열 | 전수 스캔으로 값만 확정        |
| 발견(LLM)  | 관점 5개가 지목한 항목                | 관점별로 독립 선별             |
| 카드(코드) | 24장 (아스트 2020 실측)               | 같은 대상끼리 병합 · 사슬 흡수 |
| 정렬       | 위에서부터 검토                       | 반박 판정 → 겹침 수 → 금액     |

### 핵심 통찰

1. 숫자 연산의 코드화로 환각 원천 차단
   - 증감·전기 대비 변화량을 LLM에 맡기지 않고 코드 레벨에서 확정
2. 다중 관점의 고정으로 일관성 확보
   - 역할을 임의로 방치하지 않고 고정해 다각도로 보되 방향성을 유지
3. 근거 없는 주장은 카드가 되지 못함
   - 인용 금액이 장부에 없으면 사유를 남기고 탈락, 남은 카드에도 반대 근거를 병기

## 2. 실증 예시 — 아스트 2020

정정 공시 전 원본을 넣어 파이프라인 끝까지 돌린 결과

### 분식 판정 이유

- 이미 판매된 재고자산을 매출원가로 비용 처리하지 않고 여전히 보유 중인 것으로 회계처리
- 기말 재고 과대 → 매출원가 과소 → 자기자본·당기순이익 과대

프로젝트가 지적해야 할 정답 : **재고자산 · 매출원가 · 자기자본**

### 입력 고정

- 아스트 2020 사업보고서 제출 이력 중 **최초 제출본(정정 전)** 만 분석 입력으로 채택
- 이후 정정·재작성본은 제외
- 로드 연도도 2015~2020으로 제한 — 2021년 이후 재표시 값이 영향을 끼치지 않도록

### 생성된 카드 24장

LLM 관점 5개가 각자 독립으로 본 결과를 병합해 **계정 12 · 관계 5 · 회사 7 = 24장** 생성

| 재무제표 영역 | 계정 카드                                                          | 관계 카드                           | 회사 카드       |
| ------------- | ------------------------------------------------------------------ | ----------------------------------- | --------------- |
| **재고·원가** | 재고자산                                                           | 매출↔매출원가↔재고                  | 원가            |
| 부채·유동성   | 유동성장기차입금·장기차입금·단기차입금·유동성전환사채·기타유동부채 | 차입금 조달·상환 사슬               | 유동성          |
| 자산 평가     | 무형자산·매각예정자산                                              | —                                   | 자산평가        |
| 현금흐름      | 영업활동CF·재무활동CF                                              | 당기순이익↔영업CF · 이자지급↔재무CF | 현금흐름        |
| 이익·세금     | 이연법인세자산                                                     | 법인세↔세전이익                     | 이익·세금       |
| 자본          | 이익잉여금                                                         | —                                   | 자본            |
| 우발·특수관계 | —                                                                  | —                                   | 우발·특수관계자 |
| **합계**      | **12**                                                             | **5**                               | **7**           |

- 계정 카드는 재무 수치·시계열 추세 관점(당해 급변·다년 추세)
- 관계 카드는 계정 간 관계 관점(계정 사이 괴리)
- 회사 카드는 주석·업종 비교 관점(서술 리스크·동종 대비)

| 정답 계정 | 어떤 카드로 발화           | 어떻게 잡혔나                                |
| --------- | -------------------------- | -------------------------------------------- |
| 재고자산  | 계정 + 관계 + 회사 **3층** | 재무 수치·시계열 추세 2관점 독립 지적 + 관계 |
| 매출원가  | 관계(매출↔매출원가↔재고)   | 계정 간 관계 관점이 세 계정 괴리로 지적      |
| 자기자본  | 미적중                     | 이익잉여금 계정으로만 부분 표면화            |

### 감사인이 얻는 것

곧바로 실행할 수 있는 **확인 질문**과 **감사 절차**를 반대 가능성과 함께 제공

- 검토 포인트 — 매출 −901.2억 급감에도 재고 +159.2억 증가, 재고회전율 급락. 5개년 재고 3.7배 단조 증가
- 확인 질문
  1. 재고 증가 159.2억이 원재료·재공품·제품·상품 중 어디서 났고, 장기체화 재고는 얼마인가
  2. 재고 평가충당금·저가법 반영액은 얼마이며, 매출 급감 품목에 추가 평가손실 검토가 있었나
  3. 매출 감소와 재고 증가가 같은 사업부·품목에서 났는지 대사 가능한가
- 다음 절차
  1. 재고수불부 입수 → 159.2억 증가분을 품목·사업부별로 분해하고 장기체화·저회전 리스트 대사
  2. 기말 재고실사 결과 + 후속 판매·출고 표본 검증 → 순실현가능가치(NRV) 평가 적정성 점검
  3. 매출 급감 사업부의 생산계획·취소주문·인도지연 문서 확인 → 정상 적체인지 판단
- 반박 에이전트 — "수주·인도 지연이면 재고 증가는 정상", "159.2억은 매출 감소 −901.2억의 일부"라는 정상 설명을 함께 제시하되 최종 판정은 **의심 우세**

회사명을 OpenDART에서 검색해 고유번호를 얻고, 분석 연도를 포함한 **최근 5개년**을 수집

| 수집 원천       | 범위                                                     | 처리                               |
| --------------- | -------------------------------------------------------- | ---------------------------------- |
| 본표 수치(JSON) | 재무상태표·손익계산서·현금흐름표·포괄손익·자본변동표     | 연결 + 별도 양쪽                   |
| 주석 XBRL       | 공시 원문에 기계용 태그를 달아둔 양식                    | 압축본을 XBRL 해석기 Arelle로 분해 |
| 사업보고서      | 게시 원문 전문 — 특수관계자·연결범위 등 숫자가 아닌 서술 | HTML 파서 + 정규식 헤더 매칭       |

### 정규화가 필요한 이유

- **회사별로 개별 태그를 생성** — DART 제공 XBRL은 참고사항일 뿐이라 지키지 않는 회사도 존재
- **동일 계정이 연결/별도로 쪼개져 있음** — 금액 이중계상, 또는 한쪽만 수집돼 나머지를 통째로 놓칠 위험
- **데이터 단위가 금액만이 아님** — 원화(KRW) 외에 주식 수·비율·텍스트가 섞여 계산 오류 위험

### 계정 이름 통일

```
━━━ [L1] 정규화 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  회사마다 다른 태그, 다른 표기

  ◆ 계정 이름 통일 
      1순위  표준 계정 ID   금감원 dart_* 1,313 · 국제기준 ifrs 계열 1,453
      2순위  한글 계정명    별칭 사전 1,805개
        │
        ├─ ID와 한글명이 같은 계정을 가리킴 ───────▶ 정상 매핑
        ├─ ID와 한글명이 서로 다른 계정을 가리킴 ──▶ ID를 채택하고 충돌 기록을 남김
        └─ 둘 다 실패 ───────────────────────────▶  기존 이름 유지하며 미매핑 계정 표시 ("기타 중요 계정")

  ◆ 표 구조 정리
      계열 키          "연결/별도 : 계정"  예: CFS:재고자산

```

표준 계정 사전은 **IFRS 국제표준 + 금감원 DART 확장 택소노미의 표준 ID**를 근거로 2,017종을 등재

```yaml
매출채권:
  statement: BS
  account_ids:
    - dart_ShortTermTradeReceivable # 금감원 DART 확장
    - ifrs-full_CurrentTradeReceivables # IFRS 국제표준
  aliases: [매출채권]
```

### 매핑 판정 — ID를 우선시

1. 교차표 오배정 방지 : 한글은 여러 재무제표에서 중복, 현금흐름표 데이터가 자본변동표로 섞일 위험
2. 회사의 임의 라벨링 방어 : 회사마다 한글 항목명이 달라 변동 없는 고유 번호(ID)를 우선
3. 오류 추적 및 통제력 확보 : ID 우선 + 충돌 시 기록을 남겨 오류 추적 가능
4. 자본변동표 예외 : 표준 ID 슬롯에 다른 변동을 신고하는 일이 흔해 한글 라벨을 우선

데이터 수집·이관 과정의 무결성을 6개 조건으로 검문하고, **모두 충족해야 다음 단계로 넘어간다**

| 통과 조건            | 무엇을 검사하나                                            | 차단 기준                                |
| -------------------- | ---------------------------------------------------------- | ---------------------------------------- |
| **①** 이관 완전성    | 필수 테이블 3종 적재 · 계정 소실 후보 · 자산 = 부채 + 자본 | 잔차 100만원 초과, 또는 검산 0건         |
| **②** 연산 정확성    | 한 표 안에서 합계 = 구성요소                               | 구성요소가 다 있는데 합이 안 맞을 때     |
| **③** 데이터 일치성  | 두 표에 함께 적힌 값                                       | 한 식이라도 불일치                       |
| **④** 분석 가능성    | 미매핑 금액 비중 · 핵심 표 결손 · 총계 부호                | 미매핑 20% 초과, 핵심 표 없음, 총계 음수 |
| **⑤** 계정 유효성    | 신호 엔진이 참조하는 계정명 ↔ 표준 계정 사전               | 사전에 없는 참조 1건 이상                |
| **⑥** 통화 기준 일치 | 적재된 단위 표기                                           | KRW·SHARES 외 통화 1건 이상              |

### LLM 전처리

- 별칭 자동 보정 — 표준분류가 안 된 계정 이름을 사전에 등록
  - LLM이 후보를 분석해 매핑을 선택
  - 신뢰도 0.7 이상만 자동 등록 + 5개년 전체 재정규화
  - 0.7 미만은 자동 등록하지 않고 사람이 선택
- 본문 읽기 — 사업보고서 서술형 본문을 파트별로 읽어 저장
  - 소송·특수관계·우발부채 같은 서술형 감사관심을 추출
- 비용은 회사당 약 ₩300~800 · 2~5분

    │      → 이름을 못 붙인 계정은 계정층엔 실려도 이 분석엔 못 들어감

1. 전량 투입 : 전 계정 계산값을 통째로 제공, 무엇이 중요한지는 각 관점이 직접 선별
2. 에이전트 간 정보 공유 금지
   - 판단 오염 차단 : 관점끼리 의견을 주고받으면 한 관점의 주장이 다른 관점을 물들일 위험
   - 신호 가치 : 독립적으로 발견한 결론이 겹쳐야 복수 관점 합의에 의미가 생김
   - 교차검증의 자리 분리 : 관점 간 교차는 토론이 아니라 뒤 단계 몫 — 반박 에이전트가 상대

## 5. 핵심 의사결정 — 데이터 파이프라인이 본체였다

- 초기 가설 : LLM 멀티에이전트 구축이 핵심 / 데이터 적재는 단순 준비 작업
- 실제 결과 : 작업량과 구현 병목의 대부분이 데이터 파이프라인(적재·정제) 구간에 집중

```

  수집·적재 ──────▶ 멀티에이전트 ──▶ 카드
   준비 작업          본체 

━━━ 실제 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  수집·분해·적재 ─────────────────▶ 멀티에이전트 ──▶ 카드
   조직 축 재설계 · 기록의 대부분     
                                     
```

### 분해가 어려웠던 이유와 해결

1. 계정 이름이 회사마다 다름
   - DART의 XBRL 태그 표준은 권고라 지키지 않는 회사가 많고, 같은 계정에 임의 라벨을 붙임
   - 비교 가능한 시계열을 만들기 위해 표준 계정 사전을 먼저 구축
2. 숫자와 서술이 한 문서에 섞임
   - 본표는 계정 축, 주석은 계정·카테고리 축, 본문 서술은 공시 주제 축
   - 세 축이 달라 하나의 적재 구조로 봉합되지 않음
3. 표마다 구조가 다름
   - 자본변동표는 자본거래 × 자본구성요소의 2차원이라 1차원 계정 처리를 그대로 적용할 수 없음
4. 회사·연도별 표기 방식이 바뀜
   - LG생활건강 사례 : 계정명을 "투자활동으로 인한 현금유출액"에서 "투자활동으로부터의 현금유출"로 바꾸면서 표기 부호까지 뒤집음
   - 데이터에는 `2024 +1,666억 → 2025 −1,905억`으로만 남아 **진짜 재작성과 구분되지 않음**
5. 사전에 없는 계정
   - 회사 고유 항목(예: 신종자본증권변동)과 사전 누락이 **둘 다 "미매핑"으로 동일 표시**
   - **원문 이름을 유지한 채 "기타 중요 계정"으로 게시** — 금액 소실 0
   - 표준 이름이 없으면 관계사슬·재무비율이 조회하지 못해 **전처리 화면에서 사람이 선택**

### 멀티에이전트가 한때 쓸모없어 보였던 이유

- 증상 : 내부 3관점(재무 수치·계정 간 관계·시계열 추세)이 결국 재무 수치 관점으로 수렴
- 진단 : 세 관점이 같은 연결 본문 패널만 봐 데이터 차원이 하나뿐이었음
- 해결 : 데이터층을 전면 개방 — 별도재무제표 개방 · 주석 전량 투입 · 자본변동표 2차원 편입
- 결과 : 관점마다 자기 차원의 데이터를 봐 겹침이 의미를 갖게 됨

## 8. 빠른 시작

**Docker**

```bash
# API 키 설정 (DART_API_KEY · OPENAI_API_KEY · GOOGLE_API_KEY)
cp .env.example .env

# 빌드 + 실행 → http://localhost:8501
docker compose up --build
```

**로컬 uv**

```bash
# 의존성 동기화
uv sync --group core --group agent --group dashboard --group dev

# API 키 설정
cp .env.example .env

# 테스트
uv run pytest tests -q

# 대시보드 기동 (PYTHONPATH 필요 — 리포 루트를 import 경로로 쓴다)
PYTHONPATH=. uv run streamlit run dashboard/app.py
```
