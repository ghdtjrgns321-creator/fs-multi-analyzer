# 온보딩 LLM 개선 실험 — 계획·비용·결과 추적

> 신규 회사 온보딩에서 LLM이 하는 일(계정 별칭 제안·사업보고서 청크선별·전수통독)의
> 신뢰성과 비용을 개선하기 위한 실험 기록. 무엇을 바꿨고 결과가 어땠는지 시간순으로 남긴다.
> 검증 근거: `data/backtest/_p1e2e_VERDICT.md`. 모델 선택 배경: [LLM_MODEL_COMPARE.md](LLM_MODEL_COMPARE.md).

## 1. 배경 — 검증에서 나온 문제

4개사 층화 검증(2026-06-17)에서 온보딩 LLM의 계정 별칭 제안(quirk)을 측정했다.

- 무표준코드 미매핑 계정 150건 중 LLM이 canonical 후보를 제안한 64건을 회계 기준으로 판정:
  **정확 약 48 · 회계 오답 약 7 · 애매 약 9** (적중 약 75%).
- 오답 유형: `제조원가→매출원가`, `매입액→매출원가`, `재고잔액→재고변동`, `당좌자산→유동자산`.
  표면 글자는 비슷하나 회계 실질이 다른 경우다.
- **핵심 문제**: 신뢰도(confidence)가 오답을 거르지 못한다. 제조원가→매출원가 오답에 0.88을 줬다.
  즉 "확신도 높으면 채택" 규칙은 회계 오답을 통과시킨다.
- 현재 모델은 `gpt-5.4`이고 추론강도(reasoning_effort)는 기본 미설정 상태다.

오답의 뿌리는 출력 형식이 아니라 **회계 판단**이다(이미 pydantic 출력형식을 쓰고 있다).
따라서 pydantic을 더 조여도 신뢰성은 거의 안 오른다. 개선은 추론강도·프롬프트·사람확인으로 한다.

## 2. 개선 4단계 + 측정 장치

| 단계 | 무엇 | 기대 효과 |
|------|------|-----------|
| ① 추론강도 high | `reasoning_effort`를 high로 | 회계 구분 오답 일부 감소 |
| ② 통합 1회 호출 | 별칭 제안을 계정당 → **회사당 1회**(배치) | 호출 72회 → 4회(비용·시간↓) |
| ③ 힌트 프롬프트 | 오답 유형을 일반 회계원칙으로 프롬프트 주입 | 적중률↑ |
| ④ 사람 확인 UI/UX | 확신도만 믿지 않게 근거(reason) 노출·회계판단 계정 강조 | 오답 채택 차단 |

측정 장치(반드시 지킬 것):
- **단일 변수**: ①②③을 한꺼번에 바꾸지 않는다. baseline 고정 후 하나씩 적용해 적중률을 따로 잰다.
  baseline = 위 64건 정확 48(약 75%). 각 단계 게이트 = "baseline 대비 적중률 하락 0".
- **배치 신뢰성 게이트(②)**: 계정을 한 프롬프트에 묶으면 계정 간 후보가 섞일 수 있다.
  배치 후에도 적중률이 유지돼야 채택. 떨어지면 비용 vs 정확도 판단.
- **과적합 방지(③)**: 힌트는 특정 계정명이 아니라 일반 회계원칙으로 쓴다(원가 발생≠비용화,
  잔액≠변동, 소계 범위). 힌트를 만든 4사가 아닌 **새 층화샘플**로 적중률을 검증한다(자기참조 금지).
- **회귀 가드(③)**: 힌트·배치 적용 후 기존 정답(48건)이 오답으로 바뀌지 않는지 확인.

## 3. 비용 추정

### 토큰 측정 근거
- 별칭 제안 계정당: 입력 약 420 토큰(시스템 233 + 라벨/금액/후보12개 186), 출력 약 120 토큰.
- 배치(회사당): 입력 약 1,500~5,800(계정 7~30개), 출력 = 계정수 × 120.
- 추론강도 high를 켜면 출력에 추론 토큰이 더해진다(가정 계정당 약 800 — **불확실, 가정값**).
- 단가는 gpt-5.4 공개 단가 미확정으로 **가정값**(환율 ₩1,380/$). 실제 단가 넣으면 바로 재계산.

### 실험 전체 비용 (4사 × 4단계, 새 샘플 검증 포함)

```
단계            호출수   입력토큰   출력토큰(high가정)
① high          72       30,240     66,240   ← 추론토큰이 비용 지배
② 배치          4        14,300      8,640
③ 힌트+새샘플   8        28,000     17,000
④ UI            0        -          -
합계            84       ~72,600    ~91,900
```

단가 가정별 실험 1회 총비용(추론 high 켠 경우):

| 단가 가정(USD/100만 토큰) | 실험 전체 |
|---------------------------|-----------|
| 입력 $1.25 / 출력 $10     | 약 ₩1,400 |
| 입력 $2.50 / 출력 $10     | 약 ₩1,500 |
| 입력 $5.00 / 출력 $15     | 약 ₩2,400 |

- **추론강도 high를 안 켜면** 출력 토큰이 약 1/3로 줄어(추론 토큰 제외) 실험 전체 약 ₩400~700.
- 즉 실험 비용은 사실상 무시 가능한 수준이다. 비용은 운영 전수에서만 의미가 있다.

### 운영 전수 추정 (전체 약 5,100사, 배치+high 채택 시)
- 회사당 1회: 입력 약 4,000 + 출력 약 18,000(추론 포함 가정) → 약 ₩260/회사(단가 $2.5/$10 가정).
- 전체 5,100사 1회: **약 ₩130만** (추론 high 가정). 추론 미사용 시 약 ₩20만~30만.
- 주의: 추론 토큰·단가 모두 가정값이라 실제와 차이날 수 있다. 운영 전 1회 실측 권장.

## 4. 결과 추적 (실험 진행하며 채움)

| 일자 | 단계 | 변경 내용 | 결과 | 호출수 | 실측 비용 | 판정 |
|------|------|-----------|------|--------|-----------|------|
| 2026-06-17 | baseline | gpt-5.4·reasoning 미설정·계정당 | 정확48 / 오답7 / 애매9 (≈75%) | 72 | — | 기준 |
| 2026-06-17 | ① high | reasoning high (계정당) | **실행 불가** — gpt-5.4 Chat API가 "구조화출력(pydantic)+reasoning" 동시 미지원(400). Responses API 전환 필요 | 0 | ₩0 | 보류(코드작업) |
| 2026-06-17 | ② 배치 | 회사당 1회(계정 묶음)·high끔 | **적중률 유지** — 정답·오답 baseline과 동일, 계정 혼선 0 | 4 | ₩110 | **채택 가능**(72→4회) |
| 2026-06-17 | ③ 힌트 | ②+회계힌트(일반원칙) | **오답 6건중 5건 정정**(틀린매핑→기타 보류), 제조원가 confidence 0.95→0.45로 캘리브레이션 개선. 단 애매·경계 10건도 보류(과교정·사람확인량↑) | 4 | ₩115 | **효과 있음**(precision 우선) |
| | ④ UI | confidence+reason 노출 | (미실행 — LLM 아님) | 0 | — | 별도 구현 |

**실험 총비용 ₩225** (실측: 입력 26,459 · 출력 9,669 토큰, 단가 $2.5/$10 가정). 한도 ₩5,000 대비 충분.

### 실험으로 확정된 사실
1. **추론강도 high는 현 구조로 못 켠다**. gpt-5.4는 Chat Completions에서 pydantic 출력 + reasoning을
   동시 지원하지 않는다. 켜려면 `OpenAIResponsesModel`로 전환하는 코드작업이 필요하다(단순 설정 아님).
   → "모델/추론만 바꾸면 좋아진다"는 기대는 애초에 실행 자체가 막혀 있었다.
2. **배치화는 공짜 이득**. 적중률 그대로, 호출 72→4회. 우려한 계정 혼선은 없었다.
3. **힌트가 신뢰성의 실질 개선책**. 오답을 "기타 보류"로 돌리고(틀린 매핑 제거) 오답의 confidence를
   낮춰(0.95→0.45) 사람이 거를 수 있게 했다. 대가는 보수성 — 애매한 것도 보류해 사람 확인량이 는다.
   온보딩은 틀린 자동매핑이 이중계상 위험이라, 보류 우선이 안전한 방향이다.
4. 새 샘플(다른 회사)은 무표준코드 계정이 거의 없어 **힌트 일반화는 표본 부족으로 미확정**(정직 기록).

## 힌트 생성 — 수렴 사다리 (라운드 1: 8사 목표 → 7사)

힌트는 운영 전 1회 만들어 고정한다. 오답 유형이 더 안 나올 때까지(수렴) 무표준코드 많은 회사를
층화로 늘리며 수집한다. baseline(추론 끔) 회사당 ~₩30로 거의 무료.

**라운드 1 (7사, 검증 4사 제외·무표준코드 ph≥10·8셀 층화)**: ₩246 (누적 실험 ₩471).
소금융구 셀은 corpus에 없어 7/8. 무표준코드 많은 금융·복잡회사라 신규 오답 유형이 드러났다.

신규 오답 유형 4종 (검증 6유형 외):
- **특수/구조화 상품 과일반화**: 유동화채무→기타채무·신주인수권부사채→사채·공급자금융→차입금·
  파생상품→일반금융상품.
- **폐기/처분 혼동**: 유형자산폐기손실→처분손실.
- **계속/중단영업 혼동**: 영업활동현금흐름→중단영업영업활동(c0.29).
- **자본거래 주체/방향**: 주식선택권행사→주식발행·종속기업배당→비지배배당·사업양수/양도/분할.

→ **라운드 1 미수렴(신규 4유형)**. 단 신규 오답은 대부분 confidence 0.29~0.62로 낮다(LLM이 이미
불확실을 표현). 검증의 고확신 오답(제조원가 0.88)과 다르다.

오답 유형 누적 (검증6 + 신규4 = 10): ①원가/비용화 ②잔액/변동 ③소계범위 ④순증감/단방향 ⑤자산분류
⑥귀속소계 ⑦특수상품 과일반화 ⑧폐기/처분 ⑨계속/중단영업 ⑩자본거래 방향.

## 코드 반영 + 새 회사 테스트 (확정)

라운드1이 미수렴(신규 4유형)이나 신규 오답이 저conf라, 유형 추격 대신 **일반원칙 힌트**로 확정했다.

**코드 반영** (`src/report/alias_suggest.py`):
- ② 배치화: `suggest_aliases`를 계정당 N회 → **회사당 1회**(AliasSuggestionResult). 반환 형식 불변이라
  UI(`onboarding.py`)·기존 테스트 무영향. 환각 alias(입력에 없던 라벨)는 버린다.
- ③ 일반원칙 힌트: `SYSTEM_PROMPT`에 "표면 유사≠실질, 불확실하면 기타 보류" 원칙 + 10유형을 예시로
  주입(특정 계정 하드코딩 아님). pytest 10 passed(무회귀).

**새 회사 테스트** (검증4·라운드1 7사 외 새 2사 00143651/2020·00261443/2021, 일반원칙 힌트 적용):
- **고확신(>0.85) 오답이 거의 사라졌다** — baseline의 제조원가→매출원가(0.88) 같은 자신있는 오답 없음.
- 애매한 건 저confidence(0.5~0.7)로 표현 → 사람이 거를 수 있음.
- 라운드1 신규유형(계속/중단영업·특수상품)도 정확 매핑 또는 저conf — 일반원칙이 흡수.
- → **유형을 일일이 안 쫓아도 일반원칙이 새 회사 오답까지 커버**. 두더지잡기 회피 성공.

**남은 한계**: 방향(증가↔감소)·범위(기타채권 등) 미세 오답은 저conf로 남는다. 고conf 오답(자동채택
위험)은 억제됐으니 사람 확인 + confidence 게이트로 충분히 거를 수 있다. 실험 누적 비용 ~₩800(< ₩5,000).

## 코드 리뷰 + 수정 (확정)

배치화 코드를 code-reviewer가 리뷰해 6개 이슈를 찾았고, 기능 변경이 만든 회귀를 모두 수정했다.

| 심각도 | 이슈 | 수정 |
|--------|------|------|
| P1 | 배치 1회 실패 시 전체 계정 누락 + 호출부(`onboarding.py`) None 크래시 | error 시 `result=None` → 빈 `AliasSuggestionResult` 반환, UI에 error 분기 추가 |
| P2 | 동명이표(같은 라벨 BS·IS) candidates 덮어쓰기 | `cand_map` 키를 `(정규화 라벨, sj_div)` 복합키로 |
| P2 | `unmapped_accounts` DuckDB 핸들 누수 | `with` 컨텍스트로 전환(프로젝트 표준) |
| P3 | LLM이 alias 미세 변형 시 매칭 실패로 제안 누락 | 키에 `normalize_label` 적용 + sj_div 보조 매칭 |
| P3(보류) | 파일 254줄(100줄 기준 초과) | 기능 변경과 분리해 별도 리팩토링 백로그 |

- 핵심은 P1 — **배치화가 "한 번 실패하면 전부 날아가는" 회귀**를 만들었던 것. 계정당 호출 때는 일부
  실패해도 나머지가 생존했는데, 배치는 단일 호출이라 격리가 사라졌다. 빈 결과 graceful 반환으로 방어했다.
- 검증: 전체 `pytest 263 passed · 1 xfailed`. alias 관련 11 passed(P1-B error 방어 테스트 신규 추가).

## 최종 정리 — 무엇을 했고 결과가 무엇인가

1. **문제**(검증): alias 제안 적중 ~75%, confidence가 회계 오답을 못 거름(제조원가→매출원가 0.88).
2. **시도**: ① 추론 high → **gpt-5.4 API 제약으로 불가**(Chat에서 pydantic+reasoning 동시 미지원).
   ② 배치화 → 적중률 유지하며 호출 72→4회. ③ 일반원칙 힌트 → 고conf 오답 소멸, 애매는 저conf.
3. **확정**: ②+③ 코드 반영(`alias_suggest.py`). 수렴 사다리 라운드1에서 신규 4유형 나왔으나 저conf라
   일반원칙으로 흡수, 새 2사 테스트로 일반화 확인. 코드리뷰 6이슈(P1 회귀 포함) 수정.
4. **남은 것**: ④ UI는 reason 노출이 이미 있고 error 분기 추가됨. 추론(①)은 효과 불확실+코드전환 필요로 보류.
   파일 분리(P3)는 별도 백로그. 실험 누적 비용 ~₩800(운영 전수는 하지 않음).
