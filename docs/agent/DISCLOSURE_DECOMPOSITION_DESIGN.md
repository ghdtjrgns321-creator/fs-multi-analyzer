# 사업보고서 해체 엔진 — 재설계 설계 문서

> 온보딩+Phase1을 "사업보고서 자동 분류기"로 재개념화하는 설계 단일 출처.
> 상태: **설계(미구현)**. 구현은 별도 계약/플랜에서. 브레인스토밍 합의(2026-07-06) 기록.
> 관련: [PLAN.md](PLAN.md) §3 핵심원칙 · [STATE.md](STATE.md) · 기존 issue_type 축 `src/schemas/findings.py`.

## 0. 한 줄 정체성

이 엔진은 **raw 사업보고서를 자동으로 잘라 "주제 폴더"에 정리하고, 각 폴더를 멀티에이전트(Phase2)에
넘긴다.** 정리가 좋을수록 에이전트 판단이 좋아진다 — **이 전처리(해체·정제·정리)가 프로젝트의 핵심 가치**다.

> 포지셔닝 고정: 부정을 확정하지 않는다. 해체 엔진은 "감사인이 볼 재료"를 정돈할 뿐, 판단은 Phase2가 한다.

## 1. 왜 재설계하나 (현재 문제)

현재 전처리는 두 갈래가 축이 제각각이고, 한 갈래가 신뢰 불가다.

| 원천                         | 현재 처리                                  | 문제                                                       |
| ---------------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| 본표(재무제표)               | 계정 축, 결정론 정규화                     | 견고함 (유지)                                              |
| 주석 1~41                    | 계정/카테고리 축, 결정론                   | 견고함 (유지)                                              |
| 본문 서술(I·II·IV·V·IX·X·XI) | **S7: LLM이 통째로 읽고 "중요한 것 골라"** | soft-LLM 추측 — 무엇 기준으로 고르는지 불투명, 놓쳐도 모름 |

- **S7의 결함**: LLM에 "포함 여부 + 주제"라는 두 판단을 맡긴다. 기준이 "알아서"에 가깝고, 정확도 미측정.
- **누락 사각**: 본문 서술의 상당수는 신호엔진(숫자)에 안 실려, 사람이 원문을 직접 찾아야 함.
- **근본 원인**: 서술을 "판단(LLM)"으로 다뤘다. 실제로는 **문서 구조로 결정론 정리**가 가능하다(§3).

## 2. 핵심 개념 (쉬운 말)

1. **자동 분류기**: 사업보고서를 결정론으로 잘라 주제 폴더에 넣는다. AI 추측 없음.
2. **주제 폴더**: 우발·특수관계·내부통제 같은 "감사 주제" 단위. 숫자·주석·서술이 같은 주제 폴더에 모인다.
3. **기타 폴더 + 감사인 보정**: 자동 분류가 못 넣은 것은 버리지 않고 "기타"로 모아, **감사인이 온보딩에서
   드롭다운으로 어느 폴더인지 지정**한다. 그 지정은 저장돼 다음에 재사용.
4. **커버리지 장부**: "원문을 몇 % 어느 폴더에 넣었나 + 미분류 몇 건"을 항등식으로 적어, **조용한 누락을 차단**한다.

## 3. 핵심 통찰 — 목차가 주제를 알려준다 (S7 대체 열쇠)

본문 서술의 주제는 **목차 제목으로 이미 정해져 있다.** LLM이 내용을 읽어 판단할 필요가 없다.

```
XI. 그 밖에 투자자 보호
  2. 우발부채       ← 제목만으로 '우발' 주제
V. 회계감사인의 감사의견
  2. 내부통제       ← 제목만으로 '내부통제' 주제
X. 대주주 등과의 거래내용  ← 제목만으로 '특수관계' 주제
```

`src/notes/report_parts.py`가 이미 로마숫자 PART 경계를 결정론으로 자른다. 여기에 **subsection 제목 →
주제 매핑(§6)** 을 얹으면 S7의 soft-LLM 선별이 완전히 사라지고, 판단은 Phase2에만 남는다.

## 4. 아키텍처

```
사업보고서(raw)
   │
   ├─ 본표        → [결정론] 계정 정규화 ─────────────┐
   ├─ 주석 1~41   → [결정론] 계정+주제 fact ───────────┤
   └─ 본문 서술    → [결정론] PART 전수 슬라이스          ├─▶ 주제 폴더(§5)
        ├─ 표 사실  → [구조화 API] 제재·최대주주·증자 등  │     = 계정축 근간 + 서술 부착
        └─ 프로세   → [결정론] 제목→주제 라우팅 → 청크    ┘        │ grounding 색인(§12)
                          └ 미매핑 → "기타" 폴더                     ▼
                                                              온보딩(§9): 감사인이 기타 보정
                                                                     ▼
                                          커버리지 장부(§8): 미분류 감시
                                                                     ▼
                                              Phase2 6관점(판단) — 폴더별 재료 인계(§11)
```

핵심: **모든 해체·정리 층이 결정론.** LLM 판단은 Phase2에만.

## 6. 섹션 → 주제 매핑 (제조업 표준 목차)

`report_parts`가 자른 PART/subsection의 **제목**을 주제로 라우팅한다. 제목 드리프트는 다중 패턴으로 흡수
(report_parts의 LOGICAL_PARTS 방식 확장). 아래 표는 **실제 제조업 2사(대주·삼성) 원문 전수 판정으로 근거화**
(2026-07-06, scratchpad/lowvalue_verdict_*.md). 판정: 양사 12개 섹션 중 11/12가 감사가치 있음 → 본문 대부분이

그 외 섹션별 "해당없음" 하위항목(대주 XI.2~4 등)은 데이터 부재이지 저가치가 아님.

매핑 규칙 원천 = `config/playbooks/`의 YAML(하드코딩 금지, ripple-search 대상). subsection 제목 드리프트는
다중 패턴 흡수 + 미매칭 시 "기타"로 surface(§8 장부).

## 7. 표(table) vs 프로세(prose) 분리

본문을 **데이터 성격**으로 쪼갠다 (grounding 강화 + 표 구조 보존).

- **표 형태 사실**(제재현황·최대주주·증자·배당·타법인출자 등): `_fragment_to_text`로 평면화하지 말고,
  **DART 정기보고서 주요정보 API로 구조화 수집**(`opendart.py`의 `report()`·`event()` 이미 래핑). 숫자·구조 보존.
  **수집 타이밍(Q4=A)**: `prepare_company`에서 finstate·XBRL과 함께 받아 raw 저장 → 해체 엔진은 읽기만.
- **프로세(순수 서술)**(감사의견 문구·소송 경과·내부통제 서술·MD&A): 텍스트 청크로 주제 폴더에.

> ⚠ 실측 의존 ⓐ: 어느 표 항목이 API로 실제 오는지는 **제조업 표본으로 응답 유무 대조 필요**(미검증 가정).

## 8. 커버리지 장부 (조용한 누락 차단)

기존 `src/report/coverage.py`(본표·주석 원장)를 **본문에도 확장**한다. positive-selection(골라담기)을
뒤집어 include-by-default로 간다.

- **모집단 = 전 PART 텍스트 전수.**
- **항등식**: `모집단 = 라우팅됨(주제폴더) + 정당제외(해당없음·완전 보일러플레이트) + 미분류(기타)`.
- **미분류 > 0이면 화면 경고** ("본문 ○건 미분류 — 온보딩에서 배정 필요").
- 제목 패턴에 안 맞는 섹션은 **버리지 않고 "기타" 폴더로 surface**(미매핑 계정이 "기타 중요 계정" 되는 것과 동일).

## 9. 온보딩 재정의 (한 가지 일)

현재 온보딩 = 게이트+S7+별칭 잡탕. 재설계 후 **한 문장**으로 좁힌다:

> **온보딩 = 자동 분류기가 못 넣은 "기타"를 감사인이 손으로 폴더에 배정하는 자리.**

- 게이트(정규화 품질검문 G1~G5)는 유지 — "분석 준비" 단계 소속(온보딩과 분리).
- **S7 제거** — 목차 결정론 라우팅으로 대체.
- 별칭 제안(무표준코드 계정 이름)은 유지 — 같은 "사람이 확인 후 저장" 패턴.
- 온보딩 화면 = 미분류 "기타" 목록 + 각 항목 드롭다운(주제 선택 **또는 "무시(감사 무관)"**) + 저장 버튼.

**전수 판정으로 교정됨 (2026-07-06, 대주·삼성 2사, scratchpad/lowvalue_verdict_*.md)**: 초안은 본문 다수 섹션을
"저가치=무시 대상"으로 단정했으나, **실제 원문 전수 판정 결과 양사 12개 섹션 중 11/12가 감사가치가 있었다**
(회사개요=연결범위·신용평가, 주식총수=자기주식, 주요제품=매출분해, 생산설비=유형자산 롤포워드, 이사회=자기주식취득·
특수관계거래 의결, 주주=오너일가, 임원=보수·특수관계, 우발=계열 지급보증). 따라서 **"기타=대부분 쓰레기"는 폐기.**

**"기타"에 들어오는 두 종류** (UI가 구분해야 함):
- **① 라우팅 실패(바늘)**: 제목 드리프트 등으로 자동 라우팅이 못 잡은 감사가치 섹션. → 감사인이 **올바른 폴더로 배정**.
  본문 대부분이 §6 매핑으로 라우팅되므로 기타에 남는 건 소수여야 정상(많으면 매핑 룰 보강 신호).
- **② 진짜 무시("해당없음")**: 2사 전수에서 **XI.1 공시내용 진행·변경**만 양사 공통 "해당없음". 이런
  데이터 부재 섹션만 감사인이 **"무시" 지정**. (저가치라 버리는 게 아니라 **내용이 없어서** 무시)
- UI는 ①(바늘)을 찾기 쉽게 정렬·힌트 제공(텍스트 길이·키워드) — 구현 세부.

## 10. 저장·재사용 (기억)

감사인의 기타 배정은 **영속 저장**해 다음 연도·재실행 때 다시 묻지 않는다.

- **확정(Q2=회사별 마커)**: 저장 위치 = **회사별 마커 파일**(`data/companies/{corp}/` 아래, 현
  `prep.json`/`onboarding.json` 패턴). `company_quirks.yaml` 공유 대신 회사별 격리로 깔끔.
- **오배정 방지(정직)**: 교차 회사 오염은 어느 방식이든 corp_code 키라 없음. 진짜 위험은 **같은 회사의
  작년 배정을 올해 재사용할 때 서식이 바뀐 경우** → 저장 위치와 무관하므로 **연도별 키 + 배정 재사용 전
  섹션 구조 동일성 확인(다르면 재확인 요청)** 안전장치를 넣는다.
- 배정 파일은 raw와 함께 보존(재정규화·재수집 시 삭제 금지 — 지식 유실 방지).

## 15. 스코프 · 비범위

- **스코프 = 제조업 한정.** 금융업(은행·증권·보험)은 목차 서식이 이질적이라 **제외**. 백테스트 금융사(대신증권)는 비범위.

- 분기·반기 보고서 비범위(연차 FS만) — 기존 정책 유지.
