# Phase1 감사 하니스 — 본질적 한계와 그것을 다루는 설계

> Phase1(수집·정규화)은 DART 원문을 LLM이 분석할 수 있는 형태로 가공한다. 이 문서는
> 그 가공이 "정보를 잃지 않았는가"를 검증하는 하니스가 **왜 이런 모양인지**를 정리한다 —
> 이 작업의 본질적 한계는 무엇이고, 왜 회사를 하나하나 돌리며, LLM 검사의 확률성(같은
> 검사를 시켜도 깊이가 흔들리는 문제)을 어떻게 구조로 보완했는가.
> 신호 엔진 자체의 검증은 [VERIFICATION.md](VERIFICATION.md), 백테스트는 [BACKTEST.md](BACKTEST.md).

## 1. 본질적 한계 — 왜 버그가 "계속" 나오는가

이 프로젝트의 정규화 버그는 대부분 코드 로직 오류가 아니라 **예상 못 한 입력 변형**이다.
DART 공시는 깨끗한 스키마가 아니다. 회사마다 신고 방식이 다르다:

| 실제로 만난 변형                           | 일으킨 문제                                         |
| ------------------------------------------ | --------------------------------------------------- |
| 표준계정코드 없이(blank id) 동명 계정 2행  | 유동/비유동 파생상품부채가 중복으로 오인돼 1행 증발 |
| 주식보상 변동을 주식배당(XBRL 슬롯)에 신고 | 주식선택권이 "배당금의 지급"으로 분류               |
| 손익계산서 없이 단일포괄손익계산서만 제출  | IS/CIS 행수가 어긋나 보임(실제는 재분류)            |
| 차감 변동(배당·자기주식)의 부호 제각각     | 검산 불일치 → -abs 정규화 도입                      |
| 정정공시가 원본을 덮음                     | 분식 연도 데이터가 "세탁된" 정정본                  |

이런 변형은 사전에 열거할 수 없다. **회사를 실제로 밟아야 발견된다.** 따라서 "버그가 또
나왔다"는 실패의 신호가 아니라 발견 과정의 정상 동작이다. 문제는 버그의 존재가 아니라
①발견이 운에 좌우되는 것 ②발견 전까지 조용히 데이터를 망치는 것 두 가지다.

여기에 검증 도구 자체의 한계가 겹친다:

- **기계 검사는 정의한 것만 잡는다.** 정의하지 않은 종류는 영원히 안 보인다.
- **LLM 검사는 열린 눈으로 보지만 확률적이다.** 같은 데이터를 줘도 컨텍스트 상태(긴 세션
  끝, 다른 작업의 곁다리, 빨리 끝내려는 압박)에 따라 깊이 파기도 하고 겉만 훑기도 한다.
  실제 사례: 하니스가 "소실 후보 9건"을 보고했을 때 1차 LLM 리뷰는 숫자만 읽고 넘겼고,
  재탐색에서야 9건 중 7건이 거짓 경보(의도된 부호 정규화)이고 진짜 소실은 따로 있음이
  드러났다.

## 2. 회사를 하나하나 돌리는 이유

입력 변형은 회사 단위로만 발견되므로, 검증도 회사 단위 전수로 한다.

1. **대상 전수, 표본 금지.** 검사 대상(분식 사례 회사연도)은 정답지에서 전수로 뽑아 배치로
   강제한다. "대표 1~2개 보고 통과"가 과거 사고의 원인이었다.
2. **회사마다 원문 대 산출물 직접 대조.** 같은 변환기로 양쪽을 가공해 비교하면 변환기
   버그가 양쪽에 똑같이 들어가 영원히 안 보인다(순환 비교). 그래서 DART 원문 CSV의
   금액을 가공 없이 정규화 산출물과 맞춘다.
3. **수렴을 신호로 쓴다.** 회사를 늘려도 새 변형 유형이 안 나오면 그때 "닫혔다"고 말할 수
   있다(신호 엔진 검증에서 121사 전수로 5가지 유형 수렴 — [VERIFICATION.md](VERIFICATION.md)).
   거꾸로 새 유형이 나오는 동안은 끝났다고 선언하지 않는다.

## 3. LLM 확률성을 보완하는 하니스 설계

원칙은 하나다 — **LLM이 성실하기를 기대하지 않고, 성실하지 않으면 들키게 만든다.**
하니스는 4개 장치로 이를 구조화했다.

### 3-1. 기계 바닥(floor) — 판단 이전에 못 박는 것

LLM 판단이 흔들려도 변하지 않는 검사를 기계가 먼저 깐다. 회사연도마다:

```
완결성   필수 테이블(본문·SCE·주석) 존재/비어있음
항등식   자산 = 부채 + 자본, 유동+비유동 = 총계
소실     raw 금액(절대값)이 산출물 어디에도 없는 행 수
부호반전 절대값은 보존됐으나 부호만 바뀐 행 수(의도된 정규화인지 LLM이 판정)
병합     서로 다른 원문 계정명이 한 표준계정으로 합쳐진 그룹 수
SCE      구성요소 표준화 생존 여부 + 자본변동 검산(기초+Σ변동=기말)
```

핵심 규칙: **빈 것은 통과가 아니라 실패다.** 검산 입력이 빈 집합이면 "차이 0"이 아니라
"검산 불가 FAIL"을 출력한다. 과거에 검산 입력이 전멸했는데 "기초 0+Σ0=0 차이 0"이 조용히
찍히며 정상처럼 보인 사고(hollow)가 있었고, 이를 기계로 차단했다.

### 3-2. 판정 매트릭스 — "읽었다"는 주장을 셀 수 있는 산출물로

LLM 통독의 산출물이 자유 서술이면 안 읽어도 티가 나지 않는다. 그래서 배치가
**회사연도 × 검증차원(완전성·검산·값정확·분류·주석·시계열) 매트릭스 템플릿**을 생성하고,
LLM은 각 칸을 "판정 + 원문 근거 인용"으로 채워야 한다. 별도 게이트 스크립트가
①대상 전수 존재 ②전 칸 체크 ③근거 인용 유무를 기계로 세서, 하나라도 비면 통과가 없다.
안 본 차원은 빈 칸으로 물리적으로 드러난다.

### 3-3. 전용 감사 에이전트 — 절차를 컨텍스트에서 분리

검사 품질이 세션 상태에 좌우되는 것을 막기 위해, 감사 절차·산출물 규격·**과거에 실제로
속았던 기만 패턴 목록**(부호반전 거짓 소실, 빈 검산 hollow, CIS 재분류 오인, dedup 증발,
id-label 모순 등)을 고정 프롬프트로 박은 전용 에이전트(`p1-auditor`)를 둔다. 어떤 세션에서
호출하든 같은 절차 — 배치 실행 → 전수 통독 → 매트릭스 작성 → 게이트 통과 — 로 돈다.

### 3-4. 발견 즉시 기계화 — LLM에게 같은 검사를 반복시키지 않는다

LLM 검사의 가치는 "정의 안 된 이상을 처음 발견"하는 데 있고, 반복 검사는 확률성 때문에
LLM에게 맡기면 안 된다. 그래서 LLM이 새 이상 유형을 발견하면 그 자리에서 기계 검사로
승격한다. 실례: "SCE 구성요소가 전부 미매칭"은 LLM 탐색이 발견했고, 즉시 기계 바닥
(SCE표준화 FAIL)에 추가돼 이후로는 사람이든 LLM이든 안 봐도 표에 뜬다.

## 4. 그래도 남는 한계 (정직하게)

- **소실 검사는 필요조건이다.** 우연히 같은 금액이 다른 계정에 있으면 소실을 못 본다.
  완전한 해법은 행 단위 출처 추적(provenance)이며 로드맵에 있다.
- **의미적 오매핑의 전수 검증은 기계화가 안 된다.** 금액이 살아남아도 엉뚱한 표준계정에
  있으면 분석이 오염되는데, 이는 매트릭스의 분류 차원에서 LLM이 판단하되 표본 한계가 있다.
- **하니스는 사후 감사다.** 발생 자체를 막으려면 같은 불변식을 정규화 파이프라인 안의
  검증 게이트로 옮겨야 하며(위반 시 즉시 실패), 이것이 다음 단계다.
- **게이트는 형식을 강제할 뿐 내용의 질은 강제하지 못한다.** 근거 인용을 요구해 비용을
  높였지만, 성의 없는 판정을 원천 차단하지는 못한다. 이는 반박 에이전트(중요 판정의 표본
  재검)로 보완할 수 있고 멀티에이전트 설계와 같은 철학이다.

## 5. 방법론 전환 — 라운드별 검사에서 전수 홀리스틱 통독으로 (2026-06-14)

처음에는 회사 표본을 라운드로 키워가며(5사→10사→20사) 돌렸다. 각 라운드는 표본을
재정규화하고 하니스로 검사한 뒤, 기계검사가 띄운 숫자 FAIL(자본변동표 검산 불일치 등)을
LLM이 역추적해 원인을 고치는 방식이었다. 이 방식으로 결함 유형을 여럿 잡아 고쳤다.

그런데 두 가지 한계가 드러났다.

- **기계검사는 정의한 것만 잡는다.** 자본변동표(SCE)만 전체 roll-forward 검산이 있어 거기서만
  계속 FAIL이 났고, 검산이 약한 재무상태표·검산이 아예 없는 손익계산서·현금흐름표는 "조용히"
  통과했다. "SCE만 문제"가 아니라 "SCE만 검사가 강해서 걸린" 것이었다.
- **LLM이 식(式)의 하인이 됐다.** 원래 설계는 LLM이 감사관처럼 회사 재무 전체를 읽고 판단하고
  기계검사는 바닥일 뿐인데, 실제로는 LLM이 기계검사가 띄운 숫자만 역추적하는 데 매달렸다.
  의미적 오매핑·연도 급변의 비정합·주석 분식신호처럼 **사람이 읽어야 보이는 것**을 사실상 안 봤다.
  또한 작은 표본(10사)에서 "신규 결함 0"이 나와 수렴한 줄 알았으나, 20사로 키우자 다시 결함이
  나왔다 — 작은 표본의 "수렴"은 착시였다.

그래서 방식을 바꿨다. **라운드별 식-추적 검증을 주력에서 내리고**, 지금까지 감사한 전체
회사(약 100개사·383 회사연도)를 **LLM이 감사관처럼 전수로 다시 읽는다.** 한 번에 깊게 읽을 수
있는 양(회사연도 ~10건)씩 묶어, 묶음마다 독립된 검토를 돌린다. 검토 관점은 숫자 FAIL 추적이
아니라 9개 감사 렌즈(재무 이야기 정합·연도 값 연속성·의미적 매핑·표 간 정합·주석 신호·부호
직관 등)로, 기계가 못 본 것을 잡는 데 집중한다. 발견은 셋으로 나눈다 — 정규화를 고쳐야 할
결함 / 회사 원공시 자체 특성 / 다음 단계(분식 리스크) 후보.

기계검사가 사라지는 것은 아니다. 여전히 바닥(floor)으로 깔리고, 발생을 막는 게이트로 남는다.
다만 **"무엇이 이상한가"의 판단을 다시 LLM에게 돌려준다** — 원래 설계 의도다.

남은 빈칸도 정직하게 둔다: 손익·현금흐름의 산술검산은 아직 없고(추가 예정), 신호엔진이 옛
계정명을 참조해 신호가 죽지 않았는지(신호 dangling) 점검은 전사 단위로 따로 해야 한다.

## 6. 실제 검증 결과 — 데이터 충실도(소실 0)

하니스를 돌린 결과, 가장 중요한 결론은 **가공이 원문 숫자를 잃지 않았다**는 것이다.

- **4개사 층화 표본을 DART 원문 전 항목(oracle)과 1:1로 추적**했다(규모×금융업×양식세대 직교:
  대신증권 26조·중형 1.6조·소형 1,114억·936억). 추적표 행수를 oracle 항목수와 강제로 일치시켜
  "대충 통독"으로 빠지는 사각을 차단했다.
- 결과: **원문 1,736행 전수 대조에서 재무 금액 소실 0건·금액 불일치 0건.** 앞선 6개사 E2E
  감사(삼성전자·KB금융·카카오·두산·LG화학·진양)에서도 raw == normalized로 소실 0이었다.
- 초기 자동 플래그(회사당 13~16건)는 **전부 거짓양성**이었다 — SCE 2D 별도테이블·CIS→IS 통합·
  배당 −abs 부호처럼 추적표 도구가 못 보던 사각이었고(도구경계 ≠ 감사경계), 도구 보강 후 0으로 수렴했다.
- 단, 충실히 옮겼어도 **유의성 큰데 미매핑으로 강등된 계정이 분석 입력에서 누락**되던 갭(결함①)이
  드러나 개수상한을 제거해 회수했고, **서술형 감사관심(소송·우발)이 온보딩 미실행 시 누락**되던
  갭(결함②)은 온보딩 LLM 필수화로 막았다. "소실 0"이 "분석 입력 완전"을 자동 보장하지 않음을 같이 기록한다.
